## 五項任務內容（完整背景，不引用外部檔）

### TASK-01（P0）跨網域 Cloudflare Access 架構讓所有 API 呼叫在使用者第一次使用時失敗

**現象**：PWA 登入後，瀏覽器只有 Pages 網域的 Access session cookie。任何對 Worker API 網域的 `fetch()` 會先收到 503，接著瀏覽器嘗試自動跟隨重新導向到 API 網域自己的 Access 登入頁，但 fetch 無法完成這個互動式登入流程，請求卡死。前端因此永遠停在 loading 動畫（首頁搜尋、任務頁、紀錄頁都會發生）。使用者要手動在網址列直接完整開啟一次 API 網址完成該網域自己的 Access 登入後，才會恢復正常——一般使用者不會知道要這樣做。

**指定修法**：在 `apps/web` 新增 Cloudflare Pages Functions（例如 `apps/web/functions/api/[[path]].ts`），讓 PWA 對外只呼叫同源的 `/api/*` 路徑；這個 Pages Function 負責把請求轉發到現有的 `workers/api` Worker（可用 Service Binding，在 `apps/web` 的 Pages 專案設定裡綁定 `ticket-radar-api-staging` 這個 Worker service，不需要額外的 HTTP 網路呼叫；若 Service Binding 在目前 Cloudflare 帳號設定上有困難，退而求其次可用 Pages Function 內部 `fetch()` 轉發到 Worker 的 `*.workers.dev` 網址，但要把原始請求的 method／headers／body 完整轉發，並把 Worker 回應原樣回傳，同時要小心不要把 Cf-Access-Jwt-Assertion 之類的內部標頭外洩或遺漏）。

同時需要調整：
- `apps/web/src/services/api.ts` 的 `VITE_API_BASE_URL`，Staging build 應該指向自己網域下的 `/api`（例如空字串或 `/api` 前綴），而不是 `https://ticket-radar-api-staging.vannyai.workers.dev`。
- `workers/api/wrangler.toml` 的 `env.staging.vars.CORS_ORIGIN`：因為請求變成同源，理論上不再需要跨網域 CORS，但保留現有設定以防少數情境（例如未來還是有人直接呼叫 Worker 網址測試）仍然合理，不要移除。
- 確認 `ticket-radar-api-staging` 這個 Worker 本身掛的 Cloudflare Access Application 是否還需要保留：因為現在請求會先進 Pages Function 再轉發到 Worker，如果 Worker 自己還掛著 Access，Pages Function 對 Worker 的內部呼叫也會被擋（Pages Function 沒有使用者的瀏覽器 session）。**這部分需要 Cloudflare Zero Trust 後台設定調整**，不是純程式碼能解決，請在報告中明確指出「這一步需要人工在 Cloudflare Zero Trust 後台把 API 網域從 Access Application 移除或改成允許 Service Token/Pages Function 呼叫」，不要自己嘗試登入 Cloudflare 帳號操作。

**完成標準**：
- [ ] 全新無痕視窗，只完成一次 PWA 登入（不手動導覽 API 網域），搜尋、任務、紀錄頁都能在 5 秒內顯示資料或正確的空狀態，不再無限 loading。
